§El problema

Cada año aparecen cientos de paquetes maliciosos en PyPI: typosquatting, dependencias secuestradas y código ofuscado que se ejecuta en setup.py o __init__.py. Las herramientas como pip-audit actúan después de instalar — comparan contra CVEs conocidos. Si el ataque es novel, no hay CVE; y para cuando se reporta, el código ya corrió en miles de máquinas.

"Lo que faltaba era una herramienta que mirara el código fuente del paquete antes de que pip install ejecute cualquier setup.py."

— Tesis del proyecto, oct. 2024

§Cómo funciona

pkgxray descarga el paquete sin instalarlo, descomprime el wheel o sdist, y pasa cada archivo .py por 8 analizadores AST independientes. El árbol sintáctico entiende la estructura del código, no el texto plano.

§Decisiones técnicas

Análisis estático, no dinámico

Con AST puro, pkgxray nunca corre setup.py, importa módulos ni evalúa eval(). Sacrifica detectar ofuscación dinámica avanzada, pero gana seguridad y velocidad.

Click + Rich en lugar de argparse

Click hace la CLI declarativa y testeable. Rich da tablas, paneles y syntax highlighting. Para un proyecto que vive en la terminal, son la combinación más expresiva.

Docker como distribución secundaria

Además de pip install pkgxray, imagen Docker para CI/CD donde no quieres ensuciar el intérprete del runner — escaneas y descartas el contenedor.

pytest con fixtures reales + sintéticas

Tests con paquetes reales de PyPI (cacheados) y fixtures con código malicioso conocido. 90%+ de cobertura para asegurar que ningún analizador silencia hallazgos en versiones futuras.

§Por dentro

Cada analizador hereda de Analyzer — un ast.NodeVisitor con buffer de hallazgos. El analizador de red completo son ~50 líneas:

pkgxray/analyzers/network.py ~50 líneas 
# Detecta llamadas de red sin importar el alias del módulo
import ast
from .base import Analyzer, Finding, Severity

NET_MODULES = {"requests", "urllib", "urllib3", "httpx", "socket"}
NET_METHODS  = {"get", "post", "put", "delete", "connect", "urlopen"}

class NetworkAnalyzer(Analyzer):
    name = "network"

    def visit_Call(self, node: ast.Call) -> None:
        if isinstance(node.func, ast.Attribute):
            root   = self._root_name(node.func)   # requests, urllib…
            method = node.func.attr               # get, post…

            if root in NET_MODULES and method in NET_METHODS:
                # Llamadas fuera de funciones → nivel módulo → CRITICAL
                sev = Severity.CRITICAL if self.is_module_level(node) else Severity.HIGH

                self.findings.append(Finding(
                    rule="network_access",
                    severity=sev,
                    message=f"Llamada de red: {root}.{method}()",
                    filename=self.filename,
                    line=node.lineno,
                ))
        self.generic_visit(node)

§Lo que aprendí

Publicar en PyPI no es la parte difícil. Lo difícil es decidir qué no incluir. Pasar de v0.1 a v0.2 fue mayormente borrar — identificar los analizadores con mejor ratio señal/ruido y descartar los que generaban ruido en código legítimo.

La sección de Qué NO flaggea del README — explicando explícitamente las limitaciones — es lo que más comentarios positivos recibió. Los usuarios confían más en una herramienta que conoce sus límites.

"Una herramienta de seguridad que pretende detectarlo todo es peligrosa: da una falsa sensación de cobertura. Mejor decir 'detecto X, Y, Z — para todo lo demás, mira el código tú mismo'."

— pkgxray README · sección Limitations
